# 统一为“仅流式”实现的影响评估

## 背景

当前 Tauri 侧有两种响应方式：

- **非流式**：Rust 用 `response.bytes().await` 缓冲整份 body，通过**一次** `invoke` 把完整 body 返回给 JS。
- **流式**：Rust 用 `response.bytes_stream()` 边收边通过**多次** `stream-response` 事件把 chunk 推到 JS，JS 拼成 `ReadableStream`。

统一成一种实现 = **全部走流式路径**（Rust 只做 stream，JS 只收事件拼成 `Response(body: ReadableStream)`）。

---

## 1. 对“流式”场景的影响

| 维度     | 结论 |
|----------|------|
| 行为     | **无变化**。当前 LLM/MCP 流式已走 stream 路径，逻辑不变。 |
| 性能/内存 | **无变化**。 |

**结论：现有流式效果不受影响。**

---

## 2. 对“非流式”场景的影响

当前走非流式的调用：云同步（WebDAV/Upstash/GitHub/S3）、模型列表拉取、SDK 的 `generateText` 等，都是拿到 `Response` 后做 `response.json()` / `response.text()`。

### 2.1 功能与语义

| 维度       | 当前非流式                     | 统一后（走流式）                         |
|------------|--------------------------------|------------------------------------------|
| 返回类型   | `Response`，body 为完整 buffer | `Response`，body 为 `ReadableStream`     |
| `res.json()` / `res.text()` | 可用，读完整 body 再解析       | 可用，消费流再解析，**语义与标准 fetch 一致** |
| 调用方代码 | 无需改                         | **无需改**                               |

标准 `window.fetch` 的 body 本来就是 `ReadableStream`，`.json()`/`.text()` 会消费该流。统一后行为与标准一致，**流式/非流式的“效果”在调用方看来不变**。

### 2.2 性能（延迟 / 吞吐）

| 场景           | 当前非流式                     | 统一后（仅流式）                         |
|----------------|--------------------------------|------------------------------------------|
| 小响应（&lt;10KB，如云同步单次、模型列表） | 1 次 invoke 带回整包，延迟 = 收完 body 后一次 IPC | 1 次 invoke（仅 status/headers）+ 若干次 `stream-response` 事件。首包可能更早，总时间可能略增（多次 IPC）。**影响：小响应可能多 1～2 次 IPC，延迟差异通常 &lt;10ms 级。** |
| 大响应（如 generateText 长回复） | Rust 先缓冲整份 body，再一次 IPC；内存与延迟都随 body 变大而变差 | 边收边发 chunk，不缓冲整包。**延迟与内存都更优。** |

综合：小响应可能略多几次 IPC，大响应明显更好；**整体上流式/非流式的“效果”仍可接受，且大响应更安全。**

### 2.3 内存

| 位置 | 当前非流式                     | 统一后                         |
|------|--------------------------------|--------------------------------|
| Rust | 整份 body 进内存后再一次性发给前端 | 只做流式转发，**不缓冲整份 body** |
| JS   | 一次拿到完整 body（Uint8Array） | 从 stream 读，若用 `.json()`/`.text()` 会按需缓冲，**与标准 fetch 一致** |

**结论：Rust 侧内存显著改善；JS 侧与现在用法一致，不会变差。**

### 2.4 超时与 Abort

| 能力     | 当前非流式           | 当前流式             | 统一后（仅流式）     |
|----------|----------------------|----------------------|----------------------|
| 超时     | Rust 有 timeout（如 Sync 60s） | Rust 未设 timeout    | 可在流式路径上为 Sync/LLM 等补上 timeout，**与现非流式一致或更可控** |
| AbortSignal | 未传到 Rust，取消可能不生效 | JS 侧 close 流，Rust 侧未取消 | 可保持现状或后续在 Rust 侧支持取消；**不影响“统一后流式/非流式效果”的结论** |

统一时若在流式路径上按类型设置 timeout（如 Sync 60s、LLM/MCP 300s），不会削弱当前非流式的超时效果。

---

## 3. 小结表

| 评估项           | 流式场景     | 非流式场景                         |
|------------------|-------------|------------------------------------|
| 功能/语义        | 无变化      | 与标准 fetch 一致，无行为回退      |
| 小响应延迟       | -           | 可能略多 1～2 次 IPC，影响很小     |
| 大响应延迟/内存  | -           | 明显变好                           |
| Rust 内存        | -           | 不再整包缓冲，更好                 |
| 超时/取消        | 可补齐      | 可保持或略优于当前                 |

**结论：统一成一种（流式）实现，不会削弱现有流式效果；非流式在语义和调用方式上保持不变，小响应可能有轻微 IPC 开销，大响应和内存会更好。若接受对小响应的微小开销，统一是可行且推荐的。**

---

## 4. 实现时建议

1. **Rust**：只保留“流式”一套（如 `execute_stream_request`），按 FetchType 区分 MCP/LLM/Sync 的 **timeout**（与现非流式一致）。
2. **JS**：删除 `fetchNonStream` 与流式/非流式分支，只通过一种 invoke + `stream-response` 得到 `Response(ReadableStream)`。
3. **可选**：在流式路径支持将前端的 `AbortSignal` 传到 Rust，实现真正的中途取消（当前两路径都未完全支持）。
